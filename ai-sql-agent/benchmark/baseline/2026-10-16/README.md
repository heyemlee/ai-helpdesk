# 发布门禁三轮结果（2026-10-16）

测的是 `5897af9`（`fix(retrieval): order tables by their table-level retrieval rank`），即运行记录与取消、
两处检索排序修复（`6ef8810`、`5897af9`）合入之后的 main。`5897af9` 的提交说明写着
「The full release gate on the remote embedding has not been run yet」，提交时成立；这份记录是之后补的测量。

## 结论：三轮完整轮次，每一轮八条线都过

六个类目里只有 `cross_db` 不是满分（96% / 92% / 96%）。三轮都没有走到修复，也没有降级答复；
被标为有风险的正确答案分别是 3、3、4 条。

## 三轮是怎么来的：两次运行

- **第 1、2 轮**是一次 `benchmark.gate --repeat 3`（20:32–22:27 UTC）的前两轮。这次运行的第三轮在评测集
  第 50 题之后被模型服务打断：`q051` 的抽词和规划调用各重试 5 次仍是 503，答复降级，门禁按规则不下结论，
  退出码 3。那一轮已完成的 50 题全部答对，不计入上表。
- **第 3 轮**是之后单独跑的 `--repeat 1`（22:34–23:25 UTC），退出码 0。门禁打印了「通过发布门禁」，
  同时提示单轮不足以判断达标。
- `gate.py` 判定多轮时对每项取各轮均值再比阈值。三轮按这个口径合起来同样八条全过（上表均值一列），
  但它们来自两次运行，不是一次 `--repeat 3` 直接给出的结论。

## 两道错题，都是静默错误

两题都是跨库题。筛选条件都对（上一步交过来的工程号与答对的那一轮相同），错在最后一步输出了哪些列，
校验没有拦下：

| 题 | 问题 | gold 输出 | 答错的轮次 |
| --- | --- | --- | --- |
| `q108` | 查询超预算项目的当前生产工序 | `job_no, current_process` | 第 2、3 轮输出 `work_order_id, current_process`：用工单号代替了工程号 |
| `q110` | 查询订单状态为 in_production 的工程的生产车间 | `DISTINCT workshop` | 第 1、2 轮输出 `DISTINCT job_no, workshop`：多带一列，去重的对象跟着变了 |

同一天在 `3af0475` 上退回本地向量跑的三轮完整轮次里，这两题有两轮都错，不是两处排序修复带来的。

## 引用前先读

1. **仍是演示夹具口径。** 内置演示元数据，不是部署用的语义层；这份数字不能说明真实业务库上的准确率。
2. **和 `2026-09-09` 不是改动前后的对比。** 那份用的是 `claude-sonnet-5`，代码也早得多，两份的模型和代码都不同。
3. **字段占比这条线依赖远端 Embedding。** 退回本地向量时，字段预算是每库 20 列、每表保底 4 列（远端是 10 列、
   3 列）。同一天 `3af0475` 上退回本地向量的三轮完整轮次，字段占比是 44.16%、43.69%、43.43%，都过不了
   ≤ 40%。同一后端下 `3af0475` 与 `5897af9` 选中的表和字段相同（见 `6ef8810`、`5897af9` 的提交说明），
   差别来自向量后端。
4. **三轮来自两次运行**，见上文。

## 复现

在仓库根目录配好模型和远端 Embedding 之后（见 [docs/deployment.zh-CN.md](../../../docs/deployment.zh-CN.md)）：

```bash
AI_SQL_SEMANTIC_DIR= AI_SQL_HTTP_MAX_RETRIES=5 \
AI_SQL_HTTP_BACKOFF_BASE_SECONDS=2 AI_SQL_HTTP_BACKOFF_MAX_SECONDS=30 \
PYTHONPATH=. .venv/bin/python benchmark/baseline/2026-10-16/gate_remote.py out/ 3
```

不需要逐轮明细和远端向量检查时，`make gate` 跑的是同一个门禁（`--repeat 3`）。三轮约 5.1M token。
