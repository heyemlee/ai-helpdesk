测的是 `bad6402`（`feat(prompt): SchemaGraph 标注 JOIN 基数，并要求输出主键与按需去重`）。

**这份记录的存在理由：`bad6402` 的提交说明写着「尚未测量对门禁指标的影响」，

## 两条规则的证据强度不一样，不要混着引用

改动含两条 Prompt 规则。它们的证据不是一个量级，分开说：

**规则 10（关联标注基数 + 沿一对多 JOIN 加 DISTINCT）：三轮，强证据。**
逐题明细显示这正是主要机制——两个最差类目的失败成因分布：

| | 合计失败 | 漏 DISTINCT | 投影缺列 | 其他 |
| --- | --- | --- | --- | --- |
| 改动前（3 轮） | 46 | 23 | 22 | 1 |
| 改动后（1 轮） | 12 | 1 | 9 | 2 |

折算每轮，漏 DISTINCT 由约 7.7 条降到 1 条。误伤为零：加了 DISTINCT 而 gold
没有的共 12 条，**12 条全部仍判对**。

**规则 9（输出主键）：单轮，机制证据直接但样本小。**
它的第一版措辞只写了「列举某张表的记录时」，没覆盖分组键，实测**无效**——
投影缺列那一桶没降。扩写到「按某个实体分组统计时分组键必须投影主键，
需要名称时主键与名称一起输出」之后，本该命中的两条当场翻对：

| 题 | gold | 扩写前 | 扩写后 |
| --- | --- | --- | --- |
| `q058` 统计每个供应商的采购单数量 | `supplier_id, COUNT(*)` | `supplier_name, COUNT(...)` ✗ | `supplier_id, supplier_name, COUNT(...)` ✓ |
| `q073` 统计每个物料的入库总数量 | `material_code, SUM(in_qty)` | `material_name, SUM(...)` ✗ | `material_code, SUM(in_qty)` ✓ |

全 150 题单轮对单轮：**翻对 3 条（`q058` / `q073` / `q124`），翻错 0 条。**

## 这份记录的三条局限，引用前先读

1. **上面那张三轮表测的是规则 9 的第一版**，仓库里现在跑的是扩写版。
   扩写版只有**一轮**全量（`rule9-v2-round.json`），不满足本仓库
   「至少三轮」的口径。要引用扩写版的准确率，先补两轮。
2. **`--repeat` 与 `--output` 互斥**：`run_benchmark.py` 的 `_run_repeated`
   在写文件之前就 return，`--output` 被忽略。所以三轮那次**只有汇总、没有逐题明细**，
   而 `rule9-v2-round.json` 是用六次 `--category` 单跑合并出来的。
   这是工具的坑，不是数据缺失。
3. **仍是演示夹具口径。** `AI_SQL_SEMANTIC_DIR` 置空，跑的是内置演示元数据
   （`erp_db`/`pm_db`/`mes_db`/`wms_db`），不是部署用的 `sim_erp/semantic`。
   `2026-09-08` 那份已说明这个前提性缺口，本次没有改变它。

**但基数判定本身在部署语义层同样成立**：`sim_erp` 四个库共 16 张表，
`CREATE TABLE` 与 `PRIMARY KEY` 计数一一对应（erp 6/6、prod 3/3、svc 3/3、wms 4/4），
所以主键判据取得到值。判不出时退到「多对多」这一档对主键缺失的库也是安全方向。

| 文件 | 是什么 |

| `rule9-v1-round.json` | 规则 9 第一版的全量单轮逐题明细 |

## 复现

```bash
# 三轮汇总（只有汇总，--output 会被忽略）
AI_SQL_SEMANTIC_DIR= .venv/bin/python -m benchmark.run_benchmark --repeat 3

# 要逐题明细就按类目单跑，六个类目合并成一轮
for c in single_table multi_join aggregation having time_range cross_db; do
  AI_SQL_SEMANTIC_DIR= .venv/bin/python -m benchmark.run_benchmark \
    --category $c --output round_$c.json
done
```
