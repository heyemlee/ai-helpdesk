## 关于评测数字

README 引用了两次测量，都是 150 条演示数据集、内置演示元数据。2026-09-09 那次（三轮，模型标识 `claude-sonnet-5`）有三条门禁线没过。2026-10-16 那次（提交 5897af9 上的三轮完整轮次，`gpt-6.1-sol`，远端 Embedding）每一轮和三轮均值都过了全部八条线；其中两轮来自一次在第三轮被模型服务打断的三轮运行，另一轮是单独补跑的，所以不是一次 `--repeat 3` 给出的结论。两次测量的模型和代码都不同，不能当作改动前后的对比。

两次测量都不说明真实业务库上的准确率：演示元数据不等于实际部署的语义层，2026-09-09 那次还早于现在的主键提示规则。字段占比这条线也依赖远端 Embedding：退回本地向量时字段预算放宽，同一天在 3af0475 上跑的三轮送出了 43.4–44.2% 的字段，超过 40% 的线。条件、原始记录与归因见 [2026-09-09 记录](../benchmark/baseline/2026-09-09/README.md) 和 [2026-10-16 记录](../benchmark/baseline/2026-10-16/README.md)。

## 已知限制与尚未完成的验证（截至 2026-10-16）

- **会话摘要的输入上限只做了离线验证。** 模型读到的是每条消息的有界摘录，存下来的结果保持完整。没有整体的 Prompt 预算，显式「存入知识库」的摘要路径仍然没有上限。真实多轮对话的摘要质量没有验证过。见[记忆模块的验证与剩余限制](modules/memory.md#verification-and-remaining-limits-2026-10-06)。
- **PostgreSQL 没有在真实库上验证过**这次新增的任何东西：授权里的标识符大小写规则、预览 SQL（不带 schema 限定；表结构从 `public` 读，表名靠 `search_path` 解析）、最小权限脚本的方言绑定；以及 2026-10-14 授权修复里的视图目录扫描与视图展开、整行引用（`e.*`）、拒绝把字符串当 SQL 执行的函数（`query_to_xml`、`dblink`、`set_config` 等）。只有单元测试。
- **`AI_SQL_MAX_ROWS`、`AI_SQL_MAX_EXECUTION_SECONDS`、`AI_SQL_MAX_RESULT_BYTES`、`AI_SQL_MAX_VALUE_BYTES` 只对 API 进程内的执行器生效**（默认 1000 行 / 10 秒 / 8 MiB / 8 MiB；前两个就是这两个变量没生效时实际在用的上限）。这一点在 SQLite 上验证过；PostgreSQL 分支只有用假驱动的单元测试。PostgreSQL 上字节预算只限制返回的部分，驱动已经收下的数据不受限，也没有单值上限。MCP stdio 服务固定 1000 行 / 10 秒 / 8 MiB。上限比每页行数小时，预览的一页按上限给。
- **受限策略下的视图**：策略里有任何 deny 的角色，读视图等于读它的全部基表——任一基表被拒、基表有列级限制、或视图定义解析不了，都会被拒绝。上次扫描之后才建的表或视图，要等下一次 schema 轮询或 `POST /admin/schema/reload` 后才能查；某个库的扫描失败期间，这类角色对该库的查询一律被拒。输出别名恰好和被禁列同名（`1 AS salary … ORDER BY salary`）也会被拒。详见[授权模型 §3.1–3.2](authz-model.md)。
- **数据目录先读表结构、再按调用方权限裁剪**（有缓存与单飞）；看不到的东西不会返回给调用方。
- **模型凭证被拒之后的处理只用 mock transport 验证过。** 识别「额度耗尽」「Key 停用」「模型无权限」靠的是字样表；状态是进程级的；第一个拒绝回来之前已经发出的并发请求收不回来。
- **英文界面**：语义元数据没有英文键时，数据字典的文字照原文显示；服务端的自由文本（路由原因、校验说明、错误信息）是中文。
- **路由兜底**：模型路由不可用时，规则兜底会把大部分口语化中文问法（留出集 40 条里的 30 条）判成对话而不是查数。
- **与 Helpdesk 的 A2A 联调针对运行记录这批改动跑过一次**（2026-10-17，一次流式问答，跑完并留下运行记录）。当时断开即取消还没打开，所以 Helpdesk 一侧断开的情况还没有端到端验证过。
- **取消按检查点生效。**
  - 生效时机：下一个阶段边界、两次模型调用之间、重试退避期间。
  - SQL 立即中断：SQLite 靠进度回调，PostgreSQL 由服务端取消。
  - 正在进行的那一次模型调用打断不了，因为 HTTP 客户端是同步、共享的。只能等它返回，最长为 `AI_SQL_HTTP_TIMEOUT_SECONDS`（默认 60 秒），返回结果丢弃，之后不再发起新的调用。
  - 取消和运行结束同时发生时，取消可能落空：最后一个阶段已经跑完的运行，记为 completed。
  - 调用方断开会取消这次运行（A2A 契约 v1.13 §5.4，默认开；设 `AI_SQL_CANCEL_ON_DISCONNECT=false` 可以关掉）。
  - 2026-10-16 验证过：PostgreSQL 的取消测试在真实的 PostgreSQL 16 上通过；真实模型下取消了 6 次，收到请求后 0.07–2.7 秒停下，每次都是在途的那次模型调用一返回就停。样本还小，上线后继续看 `ai_sql_run_cancel_latency_seconds`。
- **运行记录按单进程设计。** 取消请求只能找到收到它的那个进程里登记的运行，现有部署是单个 Uvicorn worker。本机进程已经退出、却还停在 `running` 的运行，启动时标为 `interrupted`；别的主机上的，超过一小时没有更新才会被标记。
