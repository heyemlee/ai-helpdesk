# 遗留 ERP 预演

`sim_erp` 那份数据有一个说清楚了的短板：字段名是业务白话（`job_no`、
`contract_amount`、`job_status='in_production'`），而**真实 ERP 抽取长的是另一个
样子**——表叫 `T_SAL_ORDER`，字段叫 `FBILLNO`、`FAMOUNT`、`FDOCSTATUS`，状态是
单字母代码，日期是 8 位整数，一行注释都没有。跑通 sim_erp 证明不了能接真库。

这个目录就是补那一课：**同一批业务事实，换一身遗留命名的皮，看质量掉多少。**

## 怎么构成的

```bash
python tools/sim_erp/legacy/build.py       # 把 sim_erp 的 15,514 行搬进 T_ 命名的 schema
python tools/sim_erp/legacy/semantic.py    # 生成遗留库的语义层
python -m ai_sql_agent.semantic validate tools/sim_erp/legacy/semantic
AI_SQL_SEMANTIC_DIR=tools/sim_erp/legacy/semantic python -m uvicorn ai_sql_agent.api.app:app --port 8000
```

数据**不重新生成**，是从 `runtime_data/sim/erp.db` 逐行搬过去的——两边是同一批
事实，所以同一个问题在两边应该得到同一个答案。答不出来，差距就精确地落在命名
这一层，而不是数据差异。

三处刻意的"真 ERP 味道"：

| 味道 | 具体 |
| --- | --- |
| 日期是整数 | `FDATE = 20260903`，不是 `'2026-09-03'`。跟"今天"比较要先转格式，两列相减也不等于天数 |
| 状态是单字母 | 订单 `A/B/C/D/E/F/Z`、应收 `O/P/S/V`、客户 `A/B`。**代码表只存在于元数据里，库本身没有** |
| 同名不同义 | 三张表都有 `FAMOUNT`：订单头是合同额、明细行是行金额、应收是开票额。光看字段名分不出来 |

## 结果：语义层把大部分鸿沟填上了

同一组 8 题，同一批数据，两边各跑一次（`compare.py`）：

| | 考点 | sim | legacy |
| --- | --- | :-: | :-: |
| C1 | 工程未付总额 = 合同额 − 已收（含未开票的尾款） | ✓ | **✗** |
| C2 | 状态码：`in_production` ↔ `FDOCSTATUS='C'` | ✓ | ✓ |
| C3 | 折让是负数，且不能只算已批准 | ✓ | ✓ |
| C4 | 零售客户信用额度为 NULL 不是 0 | ✓ | ✓ |
| C5 | 州名大小写不统一，要用规范化列 | ✓ | ✓ |
| C6 | 逾期判据 + 作废不算 + **8 位整数日期** | ✓ | ✓ |
| C7 | 没下工单的订单 | ✗ | ✗ |
| C8 | 商业工程的小区字段为 NULL | ✓ | ✓ |
| | | **7/8** | **6/8** |

**最该失败的两条反而过了。** C2 要求模型知道 `FDOCSTATUS='C'` 是"生产中"——
这个信息库里根本没有，全靠元数据里那张代码表；C6 要求它知道日期是整数、
要写 `CAST(STRFTIME('%Y%m%d','now','localtime') AS INTEGER)`。两条都对了。

**差距只有 C1 一题**，而且不是命名问题：两边都能找到对的表和字段，legacy 那边
算成了"已开票 − 已收"（18,545.89）而不是"合同额 − 已收"（49,448.16）。这是口径
定义没压住，sim 侧同一个口径也曾在轮次之间摇摆过。

C7 两边都错（真值 117，sim 答 4，legacy 答 64），是这组题里唯一一条纯粹的难题。

## 所以接真 ERP 会怎样

**能接，但工作量在写元数据，不在改代码。** 这次的证据是：字段名翻译、代码表、
日期格式、口径消歧，这四类东西写进语义层之后，模型在遗留命名上的表现和在业务
白话命名上**基本持平**（6/8 vs 7/8）。

三条不要误读：

1. **这里只有 6 张表、45 个字段。** 真 ERP 是几百张表、几千个字段，元数据的
   体量和维护成本完全不是一个量级——**难的不是难度，是规模**。
2. **代码表是靠人喂的。** `FDOCSTATUS='C'` 是"生产中"这件事，这里是我写进
   `semantic.py` 的。真库里这张表通常只存在于某个老员工的脑子里，把它挖出来
   本身就是项目里最花时间的部分。
3. **8 题的样本太小**，两边差 1 题不足以说"只差一点点"。这个结论要靠 `compare.py`
   换更多题反复跑才站得住。

## 文件

| 文件 | 作用 |
| --- | --- |
| `schema.sql` | 6 张遗留命名的表 |
| `build.py` | 把 sim_erp 的数据搬进来，同一批事实换命名 |
| `semantic.py` | 遗留库的语义层（字段名 + 代码表 + 口径） |
| `compare.py` | 同一组题在两边各跑一次，直接对比 |
