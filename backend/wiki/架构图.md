# 架构图

用 Mermaid 而不是导出的 SVG：GitHub 原生渲染，改代码时能顺手改图，
不会出现"图里画着三个 Agent、文字写着四个"这种图文不一致。

## 1. 总体架构

```mermaid
flowchart LR
    U[用户] --> FE[前端控制台<br/>React + TS]
    FE -->|/api/*| NG[Nginx]
    NG --> APP[FastAPI 服务]
    APP --> AUTH[HMAC 令牌校验 + 每用户限流]

    APP --> R[(Redis<br/>工作记忆 · 限流计数<br/>熔断与降权共享状态)]
    APP --> PG[(PostgreSQL + pgvector<br/>知识向量 / 情景记忆 / 画像<br/>工单 / 审计日志)]
    APP --> LLM[[LLM<br/>Anthropic / OpenAI 两套协议<br/>LLM_PROVIDER 一行切换]]

    APP -->|/metrics| P[Prometheus]
    APP -->|OTLP trace| OC[OTel Collector] --> TP[Tempo]
    APP -->|JSON 日志| PT[Promtail] --> LK[Loki]
    P & TP & LK --> GF[Grafana]

    classDef store fill:#1e293b,stroke:#475569,color:#e2e8f0
    class R,PG store
```

对外接口：`/chat`、`/chat/stream`、`/auth/token`、`/search`、`/skills`、
`/knowledge/*`、`/tickets`、`/eval/run`、`/eval/promote`、`/monitor`、`/metrics`。

## 2. `/chat` 主链路

```mermaid
flowchart TD
    A[请求进入] --> A2[HMAC 令牌推导 user_id<br/>每用户限流]
    A2 --> B[读取三级记忆]
    B --> C{意图识别}
    C -->|规则锚点命中| D[快通道<br/>零网络调用]
    C -->|否则| E[三路融合<br/>规则 10% + Embedding 20% + LLM 70%]
    D --> F{需要检索知识库?}
    E --> F
    F -->|快通道| G[直接检索<br/>跳过改写与重排]
    F -->|完整链路| H[查询改写 → 并行召回 → 去重 → LLM 重排]
    F -->|问候/转人工等| I[不检索]
    G --> J[领域打分路由]
    H --> J
    I --> J
    J --> K{置信度够吗}
    K -->|意图落到 OTHER 且置信度低| L[澄清追问]
    K -->|够| M[主 Agent + 辅助 Agent 执行<br/>注入 Skill SOP]
    M --> N[答案策略守卫<br/>拦截无依据的价格/时效承诺]

```

## 3. Agent 阵容与路由

```mermaid
flowchart TD
    I[意图 + 实体 + 关键词] --> S[领域打分]

    S --> T["技术可靠性 Agent<br/>TechnicalAgent"]
    S --> B["收入与合规 Agent<br/>BillingAgent"]
    S --> O["订单履约 Agent<br/>OrderAgent"]
    S -.三个专家都不达标.-> G["运营协调 Agent<br/>GeneralAgent（兜底）"]

    T -.执行失败.-> G
    B -.执行失败.-> G
    O -.执行失败.-> G

    S -.明确要求人工 / CRITICAL.-> H["运营升级通道<br/>不是 LLM Agent"]

    subgraph SK[按 Agent 类型隔离注入的 SOP]
        SK1[technical_support/SKILL.md]
        SK2[billing_support/SKILL.md]
        SK3[order_logistics/SKILL.md]
        SK4[general_customer_service/SKILL.md]
    end
    SK1 -.-> T
    SK2 -.-> B
    SK3 -.-> O
    SK4 -.-> G
```

要点：

- **三个专家按领域分竞争主 Agent**，General 只拿固定基准分，不参与专家域竞争。
- 跨域工单里达到门槛的其他专家升为**辅助 Agent**，与主 Agent 并行执行后合并结果。
- 每种类型可起多个实例；Monitor 观测到某实例劣化后，流量自动倒向同类型的健康实例。
- Skill 按 `agents` 和 `keywords` 匹配，避免不同领域的规则互相污染。

## 5. 监控与评测闭环

```mermaid
flowchart LR
    AG[Agent 实例] -->|成功率 / 延迟| MON[Monitor]
    TL[MCP 工具] -->|熔断状态 / 连续失败| MON
    MON -->|Z-score 异常检测| AL[告警]
    MON -->|monitor_penalty| RT[路由评分]
    RT -->|绕开劣化实例| AG

    EV[/eval/run/] --> ORC[真实调用编排器]
    ORC --> JG[LLM-as-Judge<br/>相关性/准确性/完整性/有用性]
    JG --> CMP{对比存档基线}
    CMP -->|退化超阈值| REG[回归项]
    CMP -->|显式 promote 才更新| BL[(baseline.json)]
```

**基线只在显式 `/eval/promote` 时更新**——每跑完一次就覆盖的话，
"相比基线退化"永远为空。

## 6. 部署结构

```mermaid
flowchart TD
    subgraph compose[docker compose up]
        FE[ai-helpdesk-frontend<br/>:5174]
        APP[ai-helpdesk-app<br/>:8000]
        NG[ai-helpdesk-nginx<br/>:80]
        R[redis]
        PG[postgres<br/>pgvector 扩展]
        P[prometheus<br/>:9090]
        OC[otel-collector]
        TP[tempo]
        LK[loki]
        PT[promtail]
        GF[grafana<br/>:3000]
    end
    FE -->|/api/ 走内网| APP
    NG --> APP
    APP --> R
    APP --> PG
    APP --> OC --> TP
    PT --> LK
    P & TP & LK --> GF
```

共 11 个服务。观测栈（Collector / Tempo / Loki / Promtail / Grafana）与业务无耦合，
不需要时删掉对应 service 即可，应用侧只是少了 trace 上报目标。

挂载 `./backend/skills`（热加载 SOP）、`./backend/data/eval`（评测基线）、
`./backend/logs`（供 Promtail 采集）。

前端容器的 Nginx 用变量 + `resolver` **在请求时**解析后端地址而不是启动时：
否则后端还没就绪，前端容器会直接 `[emerg] host not found` 起不来，
后端重启换 IP 后又会一直打到旧地址。
