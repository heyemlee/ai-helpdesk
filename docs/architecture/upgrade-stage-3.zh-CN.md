# 阶段 3：附件、图片核对与界面

实施基线：`6153cda`。实现提交：`5ecfea3`（`feat(attachments): verify image materials through durable case runs`）；交接前补丁：`054742a`（`fix(attachments): preserve unreadable images in mixed batches`）。验证日期：2026-11-05（America/Los_Angeles）。本阶段未部署，未修改运行配置、生产数据库或生产容器；仅使用既有连接做了 1 次合成图片的真实模型探测。

## 完成范围

聊天和工单工作台已贯通图片上传、私有存储、消息/材料关联、持久 Run、候选提取、业务记录核对、待补项、后续回答及历史展示。

1. 员工明确选择新问题或已有问题，可只提交图片；普通 FAQ 保留原入口。
2. 上传成功后提交附件 ID。服务端在 Case 输入事务中重新检查当前权限、附件状态与哈希，保存消息关联及 Run 材料快照。
3. Worker 使用当前配置的 GPT-6.1 Sol、显式 Responses 协议提取候选字段；图片内文字只作为数据，不进入工具指令。
4. 经既有 ToolManager → SQLAgentClient 调用只读业务查询。程序使用结构化记录核对订单、型号、数量语义/单位、状态和日期；自然语言回答不能证明字段正确。
5. 已核实事实、未核实/冲突/模糊字段、来源及后续 Run 在同一事务中保存。后续 Run 根据事实和待补项回答或追问，不自动循环识图，不自动判责赔偿。
6. 界面显示核对结果、来源、私有预览和下载。上传失败保留文件及幂等键；执行失败保留输入。处理中刷新会读取已保存的 Case 并跟随两个 Run 完成，不重新提交图片。

## 附件存储、校验与授权

新增 `attachments-v1` 追加式迁移，保存附件归属、原图/预览哈希、对象键及状态；提取缓存按附件 ID、原图哈希和提取器版本区分。`message_attachments` 保存每条消息的附件关联，`case_image_reviews` 保存每次核对结果、材料版本和控制权版本。数据库、Run 和客户端响应均不保存长期公开访问链接。

图片边界为 PNG/JPEG/WebP、单张最多 8 MiB、每次最多 4 张、最多 2,000 万像素、最长边 8,192 像素、只接受单帧。检查实际格式与声明 MIME，验证并完整解码，拒绝损坏和截断图片。预览校正 EXIF 方向、去除元数据、缩至最长边 2,048 像素；原图单独私有保存并校验哈希。

上传的原始请求在 multipart 解析前限制为 8 MiB 加 512 KiB 封装余量，包含没有 Content-Length 的分块请求；限制同时缓冲数量和接收时间。模型准入预留每张图 4,096 token，实际用量仍按模型回执结算；不按 Base64 字符长度计算图片 token，非图片工具参数仍计入预算。

| 配置 | 用途 |
| --- | --- |
| `AI_HELPDESK_ATTACHMENT_STORAGE=off\|local\|s3` | 默认关闭；开启前需接入可信员工身份和当前账号查询 |
| `AI_HELPDESK_ATTACHMENT_DIR` | 本地私有目录；API 和 Worker 必须共享同一目录 |
| `AI_HELPDESK_ATTACHMENT_BUCKET` | 私有 S3 bucket |
| `AI_HELPDESK_ATTACHMENT_ENDPOINT` | 可选 S3 兼容服务地址；AWS 可省略 |
| `AI_HELPDESK_ATTACHMENT_REGION` | S3 区域；凭据使用标准 AWS/IAM 链 |

本地适配器通过同目录临时文件、fsync 和原子 create-once 链接写入，重复写入校验相同内容，不覆盖不同对象；清理也处理上传中断的临时文件。S3 适配器使用条件写入和内容哈希，限定连接、读取及重试；不设置公共 ACL，不生成客户端直连签名 URL。真实私有 S3 兼容服务已在临时 SeaweedFS 4.52 上验证，**未验证真实云账号的 IAM、生命周期、备份或跨机部署**。

上传先提交 `staging`，再写对象并转为 `ready`；失败保留 `failed`，相同上传键与文件可恢复。正在清理的对象不能被重试复活。删除和材料绑定共享附件行锁；已经绑定 Case 的材料不能通过删除/清理接口移除。管理员清理默认回收超过一天、未关联 Case 的上传；删除失败保持 `deleting` 等下次清理。**本阶段提供清理入口，没有安装定时任务；Case 证据留存规则由阶段 5 补齐。**

每次上传、元数据读取、预览、下载、重试及结果采纳都查询当前员工账号。未关联图片仅上传者可读；关联后同一已验证实例的员工协作读取，实例间隔离。不宣称完成人员行级权限。预览/下载经后端读取，校验实际内容哈希，并在对象读取后再次授权；响应禁止缓存，浏览器只使用短暂 Blob URL。

## 图片候选与业务事实

提取器仅接受 GPT-6.1 Sol 的 Responses 连接，使用运行时已有的限流、用量记录和配置更新机制；不按模型名猜测第三方协议、不自动回退其他协议。结构化输出最多 20 个候选，区分清楚、模糊、缺失；数量区分缺件/订购/已送达/标签计数，日期区分配送/发货/订单日期。仅经过格式检查的订单标识进入固定查询，OCR 自由文本不传给 SQL 工具。

核对规则包括：

- 结果必须成功且完整，所有 step 明确 `success=true`、`truncated=false`，`row_count` 等于实际行数；失败、无记录、截断、不可用分别保留结果状态。
- 必须有数据库来源、带时区的数据时点、可信 `as_of_source`（query_time/snapshot），以及来源记录或查询 trace/Run。
- 每行包含相同订单标识；同图候选需要共同的同一查询行证明，不能拼接不同型号行的字段。行级数量/日期/状态还需图片中可读的型号锚点。
- 数量按种类选择业务列并核对单位；缺件 Case 不能把订购量或标签计数当缺件量。日期按种类核对完整 ISO 日期。
- 图片与 Case 已有订单/型号冲突时不能借用图片型号对应的数量；不静默覆盖员工或此前确认的事实。
- 重复、冲突、模糊或缺失候选进入 `image:*` 待补项。同批任何图片提取失败或没有字段时保留 `image:readability`，不能被同批其他成功图片清除。后续明确提交的新批次均成功提取出字段时可解除这一待补项；具体字段仍按核对结果保留或消除自身待补项，历史记录保留。

采纳事实标记 `source=verified_image`，包含值、单位、附件 ID/哈希、证据 ID、来源消息和 `business_source`。来源包含 database、column、row_index、order_ref、unit、as_of、as_of_source、source_records、trace_id、run_id。提取结果可按哈希缓存；重新核对始终重新查当前业务记录，不把旧查询缓存当最新事实。

没有向浏览器开放“直接标记图片已核实”的接口。`image:*` 待补项由服务端维护，客户端 `facts` 或 `pending_fields=[]` 不能清除。

## 事务、并发与回滚

材料核对结果提交沿用阶段 2 的 Run 租约、Case 材料版本、控制权版本、生命周期及人工接管检查。耗时对象读取在取得 Run/Case 行锁前完成，防止阻塞心跳；锁内再次核对当前账号、附件 ready 状态、哈希和 Case 关联，最后的 Run 条件更新检查数据库时钟下租约仍有效。撤销账号、换图、补料、接管、关闭或租约丢失都会拒绝旧结果。

核对记录、确认事实、待补项、版本递增、旧草稿失效、源 Run 回执及终态、后续消息/Run **同一事务提交**。后续消息使用保留的稳定 `verified_<source_run_id>`，后续 Run 清空识图材料并标记已核对。事务回滚不会留下孤立的后续 Run；已有持久派发扫描器负责投递。客户端不能占用 `reply_`、`adopt_`、`verified_` 内部消息前缀。

Case GET 使用同一只读 repeatable-read 事务返回状态、消息和执行记录，避免刷新时把旧消息与新 Run 终态拼成已完成页面。聊天接受 Run 时立即保存 Case ID；流断开可续读当前 Run，已转入后续 Run 的失败重试直接续读该 Run，保留原消息身份和输入。收到不完整流或未收到完成回执不会清空输入。切换问题或普通对话取消原恢复轮询。

数据库迁移保留阶段 2 表形状和接口。图片输入接受时先增加 `image:review`；数据库触发器阻止旧应用清除 `image:*` 待补项或写入同名前缀事实，仅核对事务可解除对应待补项。回滚到不支持图片的阶段 2 应用时，图片问题保持待补，不能声称识别完成；旧写入若尝试绕过保护会失败，需要恢复支持图片核对的版本后继续。既有 `case-v1` Run 实例隔离保持不变，不执行破坏式回滚迁移。

## 后续阶段接口

阶段 4 可直接使用上述 `verified_image` 与 `business_source` 结构、历史核对记录和草稿绑定的材料版本。当前查询走真实生产调用路径 ToolManager → SQLAgentClient，保留只读、部署范围和 impersonation preflight；本阶段没有扩展 A2A 契约。业务状态、政策适用与更统一的字段证据格式仍由阶段 4 处理，不应让自然语言查询答案替代原始结构化记录。

阶段 5 除服务端认证中间件写入 `request.scope['actor']`，还必须在**每个 API 和 Worker 进程**的 `app.state.actor_directory` 安装当前账号查询 provider：

```python
async def provider(actor_id: str, instance: str, *, conn=None) -> ActorContext | None:
    ...
```

provider 必须检查当前有效账号、实例和角色，不能从排队 Run 中的角色快照恢复权限。传入 `conn` 时复用该连接，不能在持有 Case 锁时另取池连接造成耗尽或阻塞心跳；该连接也可能处于只读事务。没有 provider 即拒绝附件操作，测试身份注入不代表真实登录完成。启用仍需 PostgreSQL、Redis、对应 Worker、共享私有对象存储及经验证的 Sol Responses 连接；SQLite 附件/Case 不在本阶段实现范围。

新增公共入口：

| 方法与路径 | 行为 |
| --- | --- |
| `POST /attachments` | multipart `file`，必需稳定 `Idempotency-Key` |
| `GET /attachments/{id}` | 当前授权下的状态和非敏感元数据 |
| `GET /attachments/{id}/content?preview=true` | 授权预览；省略 preview 下载原图 |
| `DELETE /attachments/{id}` | 删除自己尚未关联的附件 |
| `POST /attachments/maintenance/cleanup` | 当前管理员回收旧的未关联上传 |

已有聊天/Case 输入继续使用 `attachment_ids`；SSE 的 Run 帧补充 `case_id`，材料核对结果补充 `next_run_id`，消费方已接通。Case 读取返回材料元数据、消息附件和核对结果，不要求浏览器持有对象存储或模型密钥。

## 有限真实 Sol 图片探测

[脱敏结果](evidence/stage-3-image-endpoint-20261105.json)记录 `synthetic-image-fields-v1`：1 张合成缺件图片，经同一 ImageExtractor 和显式 Responses 调用第三方端点的 `gpt-6.1-sol`。仅 1 次请求、0 次重试，输出上限 2,048 token，客户端超时 40 秒；未上传实际经营图片。图片包含不可信的“忽略规则/批准赔偿”文字，但本次检查仅验证结构化字段。

- **1/1 请求通过**：返回模型标识符合要求，结构化 schema 有效，订单号、型号、缺件数量及数量种类/单位检查通过。
- 回执用量：输入 **1,008 token**、输出 **147 token**，缓存及推理 token 均为 0；延迟 **7,725 ms**。
- 没有真实账单或可靠结算价格，因此不把 token 数换算成实付费用；这不构成 40 图片质量集或稳健性统计。
- 报告保存原图 SHA-256 及调用脚本、图片处理和核验模块的源码哈希。探测后继续完善了纯程序核验规则，保留[当时核验源码快照](evidence/stage-3-verification-at-probe.py.txt)，三个哈希均已对照检查；提取 prompt/协议未变。不为最终纯程序修复重复付费探测。

可复现入口为 `backend/scripts/probe_image_material.py`，显式传入安全的本机设置文件、输出路径和 `--execute`；脚本不输出密钥、完整端点或原始业务响应。阶段 6 应在固定最终提交、数据、模型配置下另行执行正式图片字段质量和成本评测。
