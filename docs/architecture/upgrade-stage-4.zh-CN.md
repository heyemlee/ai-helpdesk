# 阶段 4：政策适用与结构化业务证据

实施基线：`d09e1b0`。验证日期：2026-11-06（America/Los_Angeles）。本阶段未部署，未改变正在使用的服务、模型连接、生产配置或业务数据；未调用真实模型、业务系统或真实 webhook。主对话维护的协调文档和已有未跟踪 `.codex/` 未修改。

## 完成范围

普通聊天、跨消息 Case、知识管理、SQL 查询结果和证据展示已经贯通政策范围与字段证据。金额、日期、型号、状态等关键事实从适用政策原文或经过核验的执行记录渲染；SQL Agent 的自然语言 `answer` 和图片候选文本都不能直接证明事实。草稿提交、查看和批准会重新检查引用，撤回、修改或自然过期会使旧草稿失效。

### 政策模型与请求范围

`PolicyMetadata` 包括 `status=draft|published|retired`、`version`、`effective_at`、`expires_at`、`product`、`region`、`audience`。时间必须带时区，失效时间必须晚于生效时间；发布必须有明确版本和生效时间。导入前校验整批 metadata，不能部分导入后才发现非法政策。

旧资料和没有声明政策的新导入默认是待审核，版本为 `legacy-unreviewed`，不会自动作为政策回答。管理员需逐份核对后发布。文档和片段身份纳入政策内容，同文不同版本或适用范围可并存；修改 metadata 后再次导入原范围不会覆盖已有政策。版本不是自动排序规则，适用性由状态、时间和范围共同决定。

请求使用 `policy_scope={product, region, audience, as_of}`：

- 未知维度留空，只能匹配该维度明确为 `*` 的通用政策；缺失范围不是通配授权。
- 默认按当前时间检查。显式历史 `as_of` 及员工受众要求当前可信员工身份；历史查询不把过去数据描述成现在。
- 普通聊天、Case 工作台和知识检索都有范围输入。范围随幂等请求、排队 Run、Case 快照、重试和恢复保留。
- 同一服务端上下文覆盖预取、模型工具调用、查询改写、重排和补检。工具参数不能自行扩大产品、区域、受众或时间。

SQLite 和 PostgreSQL 都在稠密/关键词排名及 `LIMIT` **之前**过滤政策。多路融合保留文档、版本和片段身份，不按相同正文合并不同政策。

缓存和持久 memo 的版本包含存储修订、Embedding epoch、请求范围及当前可用政策集合。即使没有数据库写入，政策到达生效或失效时间也会改变版本。工具循环不能通过本轮去重绕过这次检查。当前实现读取全部政策 metadata 计算时钟阶段；大规模政策库的开销留给阶段 6 测量，未宣称完成容量验收。

### 管理接口与并发更新

知识导入/上传/文档更新要求当前管理员身份；文档内容读取和检索要求当前员工身份。共享 API key、客户端 `user_id` 或排队时记录的旧角色不能替代当前账号查询。阶段 5 尚未接入身份 provider 时，这些入口保持拒绝。

`POST /knowledge/add` 的每篇文档可带 `policy`；上传接口可带 JSON 格式的 `policy` 表单字段。`PATCH /knowledge/documents/{id}` 修改政策时必须提交 `expected_revision`。metadata、内容身份哈希、`policy_revision` 和检索缓存修订在同一事务中更新；并发编辑仅一个成功，旧版本返回 409。界面支持状态、版本、范围和时间编辑，保存失败会提示刷新重审。

### SQL 字段证据与契约 v1.14

同一提交更新 SQL Agent、Helpdesk、A2A 契约、34 项 golden fixtures、版本常量、OpenAPI、实际承载者快照及前端生成类型。`message/stream`、`message/send` 和 `/query` 共享结果汇总实现。data part 现有九个必填字段，新增 `evidence` 和 `observed_at`。

每项证据保留字段和值、字段单位、数据时点及来源类型、数据库、执行步骤和行位置、查询摘要、来源记录、稳定 `evidence_id`。`entity.kind=query_row` 明确表示查询结果行，不把聚合结果伪装成业务主键。直接列来源才用于提取记录身份，不从 `MIN(id)` 等表达式制造记录主键。

`observed_at` 来自实际查询完成时间，多步取成功步骤的最早值，任一步缺失则为 null；重放或再次汇总不会续期。它与业务数据的 `as_of` 分开，历史快照可以被新查询读取。Helpdesk 默认要求原始查询在五分钟内，超时需要重新查询。

消费端逐项重算身份和摘要，检查字段、类型、值、单位、时间、来源及完整覆盖是否与执行行一致。缺项、重复、畸形字段、畸形单位/来源、行数不符，以及声明状态与步骤冲突都不能确认事实。数字没有明确单位时不从邻列或全局币种补齐；有冲突的同一业务实体字段不能相互覆盖。来源记录为空时，必须有可追溯的查询 trace/Run 和实际 SQL。

无记录、查询失败、部分成功、截断、单位缺失、过期、来源缺失和记录冲突分别保留。基础契约仍可描述部分成功；本阶段 Helpdesk 的关键事实确认采用更严格规则，要求完整成功且未截断，不从部分结果确认业务承诺。

### 图片事实与确定性答复

订单号、型号等标识保持大小写和字符身份，不能把不同标识折叠后当成同一记录。数量等字段按其语义规范化；同图多字段必须由同一实际查询行共同证明，不能跨行拼接。采纳 `db_value` 的规范化结果，同时保存图片 `candidate_value`，不以图片原始文本替代业务值。核对与材料提交均检查原始查询时间。

程序渲染业务行和字段，政策以适用原文摘录显示。模型即使在正确金额后附加另一个错误金额，或加上“仅供参考”等措辞，也不能把该值送进最终事实答复。出站金额/时效规则同样不再给予模糊措辞豁免。评测将缺失、额外捏造值和过期事实同时计入错误，不能仅凭正确数字出现判通过。

中英文答复使用 `[1]`、`[P1]`、`[I1]` 等短引用。证据卡展示实际字段、值、单位、时点和政策范围；完整 trace、查询摘要、证据 ID 和原始候选保存在可展开详情。混合员工材料和图片证据时，图片引用使用服务端分配的编号，不按全部材料位置重新计数。

普通聊天在工具循环结束后同步实际采用的证据，最终答复、证据卡、checkpoint 和事件投影的引用顺序一致。字段值按文字渲染并转义 Markdown 控制字符；聊天和草稿不会加载政策或业务字段中的外部图片。含政策原文、实际行及字段值的事件内容进入可清理的 body，不混入长期结构字段。

### Case 提交和批准

新草稿以 `evidence_version=1` 保存完整引用，政策使用 `policy_revision`，业务/图片使用稳定证据 ID 和原始时间；证据身份独立于事件 `seq`。清理事件日志不会改变已保存草稿的引用。

草稿完成事务与批准事务都重新检查政策修订、状态、适用范围和时间，以及业务证据、图片来源时间和当前权限。政策行使用当前事务的 `FOR SHARE` 锁；审批仍受 Case 材料版本、控制权版本、正文哈希和当前 ActorDirectory 约束。旧草稿缺少证据版本时不能批准，数据库触发器拒绝旧应用绕过当前证据审批。

Case GET 复用同一个只读 repeatable-read 事务，在已有连接上执行无行锁校验；不会为政策校验再次取池连接。真实 PostgreSQL 单连接池测试覆盖四个并发 GET，以及读取中途撤回政策时保持单一快照、下一次 GET 立即失效的情形。批准只记录内部确认，仍不向客户发送。

## 迁移与应用回滚边界

`kb_chunks` / `kb_documents` 的实际数据迁移到 `policy_chunks` / `policy_documents`，原名成为空、不可写的兼容视图。旧二进制读不到政策正文，旧 DDL 或写入可能被明确拒绝，不会绕过范围条件。旧资料保留但默认待审核。SQLite 迁移使用一个 `BEGIN IMMEDIATE` 事务，PostgreSQL 使用事务和迁移锁；中断回滚保留原始数据。若发现新旧同名实体表同时存在，迁移报错，要求从核验过的备份处理，不能静默取舍。

PostgreSQL 重建向量会在同一事务中处理旧名视图对向量列的依赖，成功后恢复封闭视图，失败全部回滚。回滚应用时不能把旧名恢复为可读正文的表或视图；保留新数据与保护机制，必要时旧应用进入不可检索/不可审批状态。**这属于安全关闭的应用回滚，不承诺旧应用保持全部业务可用。**

新 FAQ 队列使用 `<instance>:policy-v1`，新 Case 队列使用 `<instance>:case-v2`，防止旧 worker 领取新范围请求。阶段 5 发布切换前必须停入口并排空/处理旧队列，停止旧 worker，再切换新版本；不得把未完成的旧 checkpoint 直接搬到新命名空间。新 Run 查询不自动重放旧命名空间任务，旧 Case 历史和保存的材料仍可读取，旧草稿需重新查询后生成。数据库恢复、队列处置和发布/回滚演练仍由阶段 5/6 验证。

## 后续阶段交接

阶段 5 需在每个 API/worker 安装可信认证中间件和当前 ActorDirectory provider，检查账号、实例和当前角色，支持 `provider(actor_id, instance, *, conn=None)`，并在传入连接时复用连接，兼容只读事务。缺少 provider 时政策发布、政策内容读取与批准均按现有边界拒绝。没有新增凭客户端字段生成员工身份的临时后门。

后续部署必须同批切换 SQL Agent 与 Helpdesk 的 v1.14 契约面。旧 SQL 响应缺少原始时间/字段证据时，只能作为待核实结果，不能为了兼容补造时间或证据。阶段6应在固定提交、隔离的模拟ERP/政策数据和真实模型配置下重新测量准确性、额外错误值、性能和成本；不读取生产业务数据，本报告中的确定替身测试不代表这些业务指标已经达标。
