## 员工和数据边界

使用 PostgreSQL 本地员工目录，主动配置 `AI_HELPDESK_STAFF_AUTH=local` 与精确 HTTPS origin。生产模式缺配置、关闭身份验证或指定尚未支持的 provider 均失败关闭。无默认账号/密码、无公开注册；可信终端 bootstrap 创建首名管理员。

密码使用独立随机盐的 scrypt；登录限速由 PostgreSQL 共享，哈希工作并发上限在请求取消后仍保持，避免取消请求绕过资源限制。会话采用随机 opaque token，只存 SHA-256，HTTPS 下使用 `__Host-`、Secure、HttpOnly、SameSite=Strict cookie。固定有效期 8 小时、空闲 30 分钟，轮询 GET 不续期；修改请求检查精确 Origin 和 CSRF token。浏览器提交的 user_id、actor、role 或共享 key 不能签发员工身份。

角色区分员工、运营、管理员：普通员工能读允许受众的知识/Case、补料和读私有附件；运营能接管、审批和变更状态；账号、知识发布、模型和数据源管理要求管理员。文档列表、分页、正文、分片、分类和统计都在服务端限制受众；显式历史 as-of 不被误当作管理员权限。旧工单状态写入、慢密码计算后的账号写入、慢向量工作后的政策写入均在实际提交事务中重新检查授权。

Case/Run/附件沿用真实账号目录，入队只保存 actor ID、实例和授权版本；Worker 提交时再次查当前账号与角色。停用、改角色、改密码及退出登录会撤销旧会话/授权。流式响应在发出后续内容前检查会话。Case 完成仍遵循租约、业务版本和控制版本条件提交；业务回执不因短期 Run 清理而消失。

FAQ 原始会话/轮次和 SQL 查询历史按员工归属保护。历史会话不自动认领，管理员只能显式登记尚未归属的历史并记原因，不能随意转移已有归属。共享公司业务 Case 与原始个人会话范围分开。关联 Case 的附件重新检查账号和政策受众，上传者不能绕过限制。

浏览器经同源后端 SQL 网关访问；下游只读服务 key 与管理 key 均留在后端，前端镜像不再加载 SQL 管理 key。SQL 服务保持固定单公司只读 principal，关闭最终员工 impersonation 和跨员工长期记忆。个人查询历史先按员工过滤再分页，避免被其他员工新查询挤出；run/stream/cancel/feedback 校验归属。

前端真实登录、角色导航和操作禁用已经接入。暂时的会话检查失败保留当前输入和恢复记录；确认撤销或切换账号才清除。每个标签页记录自己的已确认身份，旧账号迟到的会话结果/401 不能覆盖新账号。真实 Chromium 双标签页场景验证了这些行为。

## 备份、保留和恢复

备份停止项目全部写入者后同时截取 PostgreSQL、SQL SQLite 状态、必要配置、私有原图/预览，执行文件 SHA-256、SQLite 完整性和业务表摘要检查，再用 AES-256-GCM 加密。密钥必须单独存放，不能在数据或备份目录内。远端上传后实际读回密文校验，不能只把“上传请求成功”作为离机备份成功。

本地默认保留 30 天、至少最新 48 份，同时永久保护当前最新和最近一次恢复验证对应的快照，直到有新的合格锚点。默认 `prune` 只预览；显式应用或配置的成功备份后清理才删除。无验证、锚点缺失、清单变动时停止删除；未知文件与符号链接不删。没有自动删除远端备份；真实云端生命周期/Object Lock 策略尚未验证。

每日验证使用独立临时数据库，先核对实际密文摘要，再核对恢复清单时间戳，恢复业务数据和对象，不启动应用/Worker。验证、备份、保留共用锁。替换为另一份仍合法加密的旧快照会失败，不刷新成功时间。API 只读独立的非敏感时间戳文件，私有快照/候选环境不挂载到 API；发布成功不会冒充恢复验证成功。

实际恢复全部成功后，账号先关闭、会话清空，旧授权不能自行复活。须提交当前人员和角色复核，再进行员工/Case/附件/SQL 网关检查。必要配置被恢复到 `config/deployment`，不会自动覆盖现行外部 `.env`；域名、云凭据、SQL key 等须核对。最终演练特意轮换外部 SQL 服务 key，使其与恢复的 SQL key 清单不一致：Case 与附件仍可读、SQL 进程也就绪，但真实员工经 `/sql-api/whoami` 得到 502 服务不可用，Worker 和入口保持关闭。下游凭据拒绝不再冒充员工 401，员工会话与恢复记录保留；真实员工授权撤销仍返回 401 并清理。修正配置、重新完成恢复与复核后才开放。

恢复后的对象校验读取真实目标，而非只检查解包文件。S3 演练中故意损坏目标对象并让上传步骤假装成功，实际哈希校验拒绝开放。另有密文损坏和 PostgreSQL 已恢复、配置目录恢复中途失败的反例；均确认写入者关闭、真实入口拒绝连接/503。

RTO 从本次成功恢复开始，到人员清单自动复核、真实员工内部业务/SQL 网关检查、服务启动以及**真实已发布本机端口**身份限制验证成功为止。PostgreSQL/Redis 容器已在运行，不含新主机或存储重建。人工复核由事先准备的合成清单完成，没有把人工等待时间算入；真实 HTTPS/DNS、离机下载和生产规模未计入。早期约 11 秒的内部冒烟结果不作为最终 RTO。

观测 RPO 窗口是快照时点到模拟丢失时点的间隔。每套直接向临时数据库插入一笔快照后的合成 Case 动作，再恢复到快照，确认这 1 笔写入丢失。它说明快照恢复有数据损失窗口，不能解释为生产 RPO 只需几十秒。小时计划的预算约为一小时加调度、快照完成/上传时间；尚无生产连续运行数据证明这一目标。

## 发布、回退和旧版本限制

CI 门禁后从同一提交构建三份镜像，临时环境验证后才允许发布相同完整 ID。两份报告、initial/reopened 阶段都绑定 backend/frontend/sql 映射；同提交重建得到不同 ID 或缺服务映射都会拒绝。发布时关闭入口，业务检查前不启动 Worker/SQL；SQL 启动后再验证员工网关及固定只读身份，最后启动 Worker 并开放。实际 `release.env` 原子保存新版本，避免重启回到旧标签。

故障候选由真实安全后端镜像派生，启动立即退出。两套最终演练都实际触发失败并回退到已验证的三份安全镜像，重新验证后开放；没有只把 manifest 改成成功状态。回退不自动降级数据库，失败则继续维护。当前最低安全版本是本阶段新构建版本，不是此前已发布过的版本。

只读确认当前旧生产后端镜像为 `sha256:e3bd5c98419a4936937157ad70bcf59597126e48a6f0d1827f46d3eca947d404`，随后仅在独立临时项目使用该真实二进制启动，连接已恢复的升级数据库。启动退出码 1，错误为对视图 `kb_chunks` 执行 `ALTER ... ADD COLUMN`。启动前后业务摘要一致，未允许开放。旧版又不具备新的员工会话边界，因此不把它作为安全回退目标；这项兼容性失败明确保留，不能声称“旧生产版启动/回退通过”。

开发中发现并修复的失败没有计入最终通过：

1. 首轮本地恢复、损坏密文和中途失败关闭已通过，但故障镜像构造错误地使用 `FROM sha256:<本地 ID>`，被 BuildKit 当作 registry 名称而失败。该轮未完成发布回滚。改为从精确镜像创建临时容器、提交故障 CMD 后，才完成真实失败/回退。
2. 首轮 S3 项目仅连接 internal 网络，声明的主机端口没有可达绑定，出现 `EndpointConnectionError`，没有完成 S3 备份/恢复。修正对象服务与 ingress 网络后，增加真实本机入口的维护关闭/恢复后可达检查，并重跑两套最终演练。
3. 后端新增目录授权后，一条旧测试仍预期共享 key 可访问分类目录；修正为必须员工身份。前端新增会话测试最初缺浏览器 storage fixture，补齐后 428 项通过。这些是测试迭代失败，不被当作生产故障或最终跳过。
4. 早期内部冒烟、未绑定最终镜像/真实入口的中间成功尝试仅为开发证据，不用其 RTO 作为最终验收。最终报告附完整镜像映射与运维文件摘要。
5. 网关复核发现下游 SQL 401 会触发前端退出员工会话；改为 502 并增加后端和前端回归。旧 401 反例的中间演练结果不替代最终版本，两套最终演练都重新使用包含此修正的镜像。
