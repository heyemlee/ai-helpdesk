# `/auth/token` 接可信登录身份：现状、结论、对接方案

> **先说结论，因为它是一个"还没做"的答案，不能让它看起来像做完了。**
>
> **把令牌签发接到可信登录身份这件事，本轮没有做，因为它依赖一个本仓库里
> 尚不存在的组件。** `grep -riE 'oidc|oauth|saml|sso|keycloak|auth0|okta|ldap'`
> 在 `backend/` `frontend/` `docs/` 下**零命中**——这个项目没有登录系统，
> 也没有对接任何外部身份提供方。
>
> 本轮做的是另外两件：把过渡形态的**约束从文档搬进代码**（下面第二节），
> 以及把**接什么**写清楚（第三节），免得等真有登录系统时再从头讨论。

---

## 一、现状与它到底能证明什么

`POST /auth/token` 按请求体里的 `user_id` 签发 HMAC 令牌，
`/chat` 之后用这个令牌推导可信身份、隔离记忆与限流。

它的鉴权链条今天是这样：

| 层 | 做什么 | 能证明什么 |
| --- | --- | --- |
| `require_admin_key` | 校验 `X-API-Key`，**未配置时不放行**（一律 503，不看 `APP_ENV`） | "调用方持有管理密钥" |
| `require_token_issuer_source` | 校验**直连对端**在 `AI_HELPDESK_TOKEN_ISSUER_CIDRS` 里 | "调用方来自网关所在的网段" |
| —— | —— | **证明不了"这个 `user_id` 真的登录了"** |

差距就在最后一行。管理密钥是一把**共享**钥匙，它是基础设施的凭证，不是用户的凭证。
换句话说：**任何能调到这个端点的组件，都能为任意 `user_id` 拿到有效令牌。**
今天靠"只有网关能调到"把这个集合压到最小，但压小不等于消除。

风险边界（写清楚，免得被当成已解决）：

- 网关本身被攻破 / 网关上跑的任意代码 → 可以冒充任意客户读其记忆上下文；
- 内网横向移动到白名单网段 → 同上；
- **不构成风险的**：公网直接打这个端点（来源不在白名单 → 403）、
  漏配管理密钥（→ 503，不是放行）、漏配白名单（生产模式**进程起不到**）。

## 二、本轮做了什么：把约束从文档搬进代码

上一轮把"只暴露给网关"写进了 README 和部署文档。那是对的做法，
**但它是说明，不是修复**——约定不会在配错的时候报错。所以：

| 位置 | 强制什么 |
| --- | --- |
| `core/preflight.py::check_token_issuer_binding` | 生产模式下 `AI_HELPDESK_TOKEN_ISSUER_CIDRS` 必须配，且**不能是 `0.0.0.0/0`**——允许一切等于没有约束，而配置文件看起来是有的。不满足**拒绝启动** |
| `core/preflight.py::token_issuer_networks` | 拼错的 CIDR **直接抛**，不忽略。忽略等于白名单被悄悄放宽 |
| `api/main.py::require_token_issuer_source` | 每次请求校验**直连对端**。拿不到对端地址时**拒绝**——"无法确认来源"和"确认了不合法"，对一个签发身份的端点是同一件事 |

**为什么判直连对端而不是 `X-Forwarded-For`：** XFF 是一个请求头，任何人都能写。
拿它当来源判据，等于把白名单交给调用方自己填。只有直连对端是传输层事实。
代价是白名单里要写**网关**的地址而不是最终客户端的——那正是想要的语义。

用例：`tests/test_preflight.py::TestAuthTokenIsBoundToTheGateway`（启动断言）、
`::TestAuthTokenSourceIsCheckedAtRequestTime`（请求路径，含
`test_x_forwarded_for_cannot_get_past_it`）。

配置示例：

```env
APP_ENV=production
AI_HELPDESK_API_KEY=<管理密钥>
AI_HELPDESK_AUTH_SECRET=<32 字节随机>
AI_HELPDESK_PROTECT_CHAT=true
# 只填网关/入口所在的网段。留空或写 0.0.0.0/0 → 生产模式拒绝启动
AI_HELPDESK_TOKEN_ISSUER_CIDRS=10.42.0.0/16,127.0.0.1/32
```

## 三、真有登录系统时接什么（对接方案）

这一节是给"那天"准备的。三个问题，答案定下来就能实现。

### 1. 谁签发

**由登录系统签发，`/auth/token` 退役。** 不要保留"登录系统调 `/auth/token`
换一个我们的令牌"这种两段式——那只是把共享密钥的问题往上挪了一层，
`user_id` 仍然是**调用方声明**的，而不是**被证明**的。

推荐形态：ai-helpdesk 直接验登录系统签发的令牌。

| 登录系统类型 | 我们这边做什么 |
| --- | --- |
| OIDC（Keycloak / Auth0 / Okta / Entra ID 等） | 从 `issuer` 的 JWKS 拉公钥，验签 + `iss` / `aud` / `exp`，`UserTokenAuth` 换成 JWT 校验 |
| 内部 SSO，能签 JWT | 同上，公钥由内部提供 |
| 内部 SSO，只有 session cookie | 由网关校验会话，并**在网关上**换成我们的令牌——这时 `/auth/token` 可以保留，但它的调用方必须是那个校验过会话的网关组件，而不是任意持有管理密钥的东西 |

### 2. `user_id` 取哪个 claim

**要求：全局唯一、不可重用、稳定。**

- **优先 `sub`。** 它就是为这件事定义的。
- **不要用 `email` / `preferred_username`。** 它们会变，而且可以被回收——
  一个离职员工的邮箱被重新分配给新人，新人就继承了旧记忆和旧画像。
- 需要租户维度时，另取一个 claim（见
  `docs/sql-agent-identity-requirements.md` 第 4 条：下游要做行范围，
  可能需要租户号，那时这个 claim 要一并定下来）。

**约束一条：`user_id` 里不能有 `.`**（`core/auth.py::issue` 已经在拒绝了）——
现在的令牌是 `user_id.expires_at.signature` 三段式，用 `.` 分隔。
换成 JWT 之后这条约束消失，但**换的那一刻要一起改**，不然是一个静默的解析歧义。

### 3. 令牌生命周期怎么对齐

- **我们的令牌不能比登录会话活得久。** 今天默认 TTL 是 86400s
  （`UserTokenAuth.default_ttl_s`），这个值是拍的，不对应任何真实会话。
  接上之后取 `min(登录令牌 exp, 我们的上限)`。
- **登出要能生效。** HMAC 令牌是自包含的，签发之后撤不回。要支持登出，
  要么把 TTL 压到分钟级并依赖刷新，要么引入一份撤销名单（Redis 已经在链路里）。
  **这是一个要显式决定的取舍，不要默认落到"撤不回"。**
- 时钟：`exp` 的校验两边都用 UTC，允许一点偏移（今天是零容忍，
  `expires_at < time.time()` 直接判过期）。

### 4. 迁移期怎么走

1. 先加 JWT 校验路径，与现有 HMAC 令牌**并存**（按令牌形状分派）；
2. 前端 / 网关切到登录系统签发的令牌；
3. 观察一个完整的令牌生命周期，确认没有回落到旧路径；
4. **删掉 `/auth/token` 与 `UserTokenAuth.issue`**，并把
   `AI_HELPDESK_TOKEN_ISSUER_CIDRS` 这条启动断言一并去掉——
   它是过渡形态的补丁，端点没了它就该没。

> 第 4 步是这次改动"真的做完了"的判据。留着一个还能签发身份的端点，
> 前面三步做得再好也只是多了一条路，不是换了一条路。
