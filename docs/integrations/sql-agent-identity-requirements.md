# 给 ai-sql-agent 的需求：身份传递与权限解析（调用方，2026-09-05）

你们这一轮要做两件事——给 `DataPolicy` 加行范围维度、impersonation 时按最终用户
重新解析策略并与服务身份取交集。**在动手之前，这份文档说清楚调用方会传什么、
传到哪一层、期望你们怎么解析。** 等设计完了再对齐会贵得多。

审查结论（2026-09-04，用 alice / bob 两个客户身份实测）：**今天的
impersonation 只换 `user_id`，保留服务密钥的角色和策略，不会为最终用户重新
解析权限——两个身份看到的数据完全相同。** 所以这条链路今天不能靠"有 user_id"
保证客户只读到自己的数据，ai-helpdesk 这边已经把"单租户、业务数据不按客户隔离"
写进了 README 和部署文档。下面是把它变成真隔离所需要的东西。

---

## 一、我们今天传什么

`POST /query` 与 A2A 两条都一样（`backend/app/tools/sql_agent_client.py`）：

| 字段 | 值 | 说明 |
| --- | --- | --- |
| `user_id` | `SQL_AGENT_IMPERSONATE=false`（默认）→ 服务身份 `SQL_AGENT_USER_ID`；`true` → 最终用户的可信 id | 这个 id 由服务端从 HMAC 令牌推导（`AI_HELPDESK_AUTH_SECRET`），**不是请求体里客户端自己填的那个** |
| `session_id` | `hd-<sha256(可信 user_id + 本方 conv_id)[:32]>` | **2026-09-05 起改成派生值**，见下 |
| `X-API-Key` | 服务密钥 | |

### `session_id` 变成了不透明派生值，请按不透明处理

原先直接把本方的 `conv_id` 发过去。而 `conv_id` 是**请求体里客户端自己填的**,
在共享服务身份下，客户 A 填上客户 B 的 conv_id 就能让 B 的下游会话记忆注入
自己这轮的上下文——一条没有任何症状的跨客户串话通道。现在它绑定到认证身份：

```
session_id = "hd-" + sha256(f"{可信user_id}\0{conv_id}").hexdigest()[:32]
```

对你们的要求只有三条：

1. **当成不透明字符串**，不要解析、不要从里面提取任何东西（提取不出来，是摘要）；
2. 会话记忆**严格按它分隔**，不要再叠加别的分隔维度，也不要少用它；
3. 长度固定 35 字符（`hd-` + 32 hex），字符集 `[a-f0-9]`。如果你们那边对
   `session_id` 有长度或字符集限制，现在说。

代价是你们的日志里看不到我们的 `conv_id` 了。对账走 `trace_id`：
我们两边都记它，我们这边的日志行还额外带 `session=`（`sql_agent.query 完成` 那一行）。

## 二、我们需要你们做什么

按重要性排，前三条是**安全属性**，缺一条这条链路就不能对外称作按客户隔离。

### 1. impersonation 必须重新解析权限，并与服务身份**取交集**

期望语义：

```
最终可见范围 = 服务密钥策略 ∩ 最终用户策略
```

- **交集，不是并集，也不是替换。** 服务密钥的策略是这条链路的上界
  （我们按"能接触到本客服系统的最不受信任的访客"来配它）；最终用户的策略
  只能在这个上界内再收窄，**永远不能放宽**。
- 一个具体的要求：**impersonation 打开时，最终可见范围不得大于 impersonation
  关闭时**。如果实现出来会更大，那说明方向反了。

### 2. 解析不了最终用户时**必须失败**，不能回落到服务身份

这一条单独列，因为它是最容易被写成"容错"的地方：查不到这个 user 的策略 →
用服务身份继续跑 → **静默提权**，而且链路完全正常、没有任何症状。

期望：`SQL_AGENT_IMPERSONATE` 打开且最终用户解析失败时返回明确错误
（我们会按委派失败处理，转人工，客户拿到的是"这次没查到系统记录"，
不是一段没有依据的答案）。**不要回落。**

这与契约 §4.6.7「缺失 = 不可信」是同一条原则：一个降低权限的信号缺席时，
若按"没有这个信号"处理，等于默认放行。

### 3. 告诉我们**实际用了哪个身份**——否则我们没有任何字段能发现它退化了

这是契约 §4.6 那类缺口的重演：`queried_database` 在"查成了"和"查挂了"两种
情况下都是 `true`，于是调用方分不出来。身份这一层今天有完全一样的问题——
我们请求了 impersonation，但**收不到任何字段能确认它真的生效了**。

建议在 data part（三个承载者同构，契约 §4.4.1）里加：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `resolved_principal` | string | 实际用于解析策略的身份 |
| `principal_source` | `"end_user"` \| `"service"` | 是最终用户还是服务身份。**与契约里的 `status_source` / `currency_source` 同构** |
| `policy_scope` | string \| null | 实际生效的策略标识（能对上你们审计里那一条即可） |

有了 `principal_source` 我们就能加一条断言：请求了 impersonation 却拿回
`"service"` → 判为不可作出处。**没有它，退化是静默的。**

### 4. 行范围（租户）维度：我们能提供什么

你们要给 `DataPolicy` 加行范围，需要一个租户/客户维度的键。我们这边可提供：

| 我们能给 | 可信度 | 说明 |
| --- | --- | --- |
| 最终用户 id | **可信**（HMAC 令牌推导，客户端伪造不了） | 就是上面那个 `user_id` |
| 租户 / 客户号 | **今天没有** | 我们的令牌里目前只有 user_id。要传租户号，需要先在令牌里加一个 claim——这是我们这边的改动，**告诉我们你们需要什么形状，我们来加** |

请明确两件事，我们照着做：

1. 行范围的键你们想要什么粒度（用户？客户号？项目号？）；
2. 它应该走请求字段还是走你们侧的用户目录（我们传 id，你们查映射）。
   **我们倾向后者**——映射表放在数据那一侧，我们这边就不用维护一份会漂的副本。

### 5. 被策略拒绝要和"查到了但没有"分开

`ResultSummary` 里已经有 `denied_tables`，但它**没有进 data part**。
对客户来说这是三句不同的话：

- 查到了，答案是没有记录（`execution_status=no_data`）；
- 没查成（`failed`）；
- **你无权看这部分**（今天落进上面某一个，分不出来）。

第三种我们需要能识别——它不该被讲成"系统里没有这条记录"。
建议把 `denied_tables` 放进 data part，或者给 `execution_status` 加一个值
（加值是契约变更，走 §6；放字段更轻）。

### 6. 审计对得上

我们这边每次委派都记 `trace_id` + 派生的 `session_id`。请你们在同一个
`trace_id` 下记 `resolved_principal` 与 `policy_scope`——出纠纷要复盘
"这个数字当时是以谁的权限查出来的"，只有两边都记了才追得回来。

## 三、我们**不会**做的事

写出来免得你们按错误的假设设计：

- **不会**把客户端请求体里的 `user_id` 直接传下去。传下去的一律是令牌推导出来的
  可信身份；令牌鉴权没开的部署（demo）一律传服务身份。
- **不会**在调用方这边做行级过滤。拿回来再过滤等于数据已经出库了，
  而且我们没有权限元数据。**租户/行范围最终要下沉到数据库**，这一点两边一致。
- **不会**把 `session_id` 当权限维度用。它是会话隔离，不是授权。

---

## 四、排期上的一个请求

第 3 条（`principal_source`）**比第 1、2 条更早需要**，虽然它更小。

理由：1、2 是能力，3 是**可观测性**。在 1、2 落地之前，我们这边只能按
"业务数据没有按客户隔离"对外表述；1、2 落地之后，我们需要一个字段来断言它
真的生效了，否则我们只是把"相信它有效"从一个仓库搬到了另一个仓库。
而这类缺口的历史是：没有可断言的字段时，两侧都会以为对方做了。
