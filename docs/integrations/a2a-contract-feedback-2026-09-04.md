# 交回 a2a-contract 的问题清单（调用方，2026-09-04）

对照 tag `v1.6`（`1f943d0`，与该仓库 `main` 的 `293c203` 内容一致）实现调用方那一半时
发现的六条。**没有为了让契约成立去改契约，也没有单方面改实现去对齐一个还没改的契约**
——凡是实现上不得不先做一个决定的，下面都写明了做的是哪个决定、依据是什么。

按要紧程度排序。前三条会影响两侧对同一份载荷的判定，后三条是文档一致性。

## 1. 「字段缺失」与「字段尚未实现」被混成了一件事（§4.6.7 vs §4.6.8）

**问题。** §4.6.7 的表说 `execution_status` 缺失按 `failed` 处置、
`result_truncated` 缺失按 `true` 处置。但这两个字段今天都还没有实现
（前者标 🔨，后者标 ➕），也就是说**每一份线上载荷都缺这两个字段**。
照字面执行，结果是：

- 所有查询一律 `failed` → 一条都不能当出处 → A 组（`dp-valid-01` 等）全红；
- 所有结果一律按截断处置 → 任何"共有 N 条"的表述都不成立。

而 CONSUMER-TESTS 自己提醒过"一个永远返回不可信的实现能过 B 组但会让 A 组挂，
**两组必须同时绿**"。所以照字面执行是过不了自家用例的。

§4.6.8 的表其实给了正解——「查询是否真的跑成了」那一行写着
"🔨（今天只能自己 reduce `steps[].success`）"——但它在正文里是一句括注，
不在 §4.6.7 那张规范性的表里。两处并排读是矛盾的。

**我方做的决定。** 按三档处置，并把来源记在 `status_source` 上
（`backend/app/core/evidence.py` 的 `derive_execution_status`）：

| 情况 | 处置 | `status_source` |
| --- | --- | --- |
| 服务端下发了 `execution_status` | 直接采信 | `contract` |
| 没下发，但 `steps[]` 在 | 按 §4.6.1 的判据从 `steps[]` 推导 | `derived` |
| `steps[]` 也拿不到 | `failed` | `missing` |

`result_truncated` 同理：顶层字段有就用，没有就看 `steps[i].truncated`
（那个今天在线上），两者都没有才按 `true` 处置。

**建议契约怎么改。** 在 §4.6.7 的表上方加一句区分：
「本表说的是**契约已要求、实际没送到**的字段。标 🔨/➕ 的字段在服务端实现之前
按各小节给的**过渡判据**处置，不落进本表。」然后把 §4.6.8 那句括注提级为
§4.6.1 的一段正文，写清楚过渡期就是从 `steps[]` 推导——因为**它现在是规范，
不是权宜**：两侧都在照它做，只是契约没写。

## 2. `dp-trust-01` 的 `xfail` 指示与它自己的断言冲突

**问题。** CONSUMER-TESTS §C 与 `fixtures/index.json` 都说
`dp-trust-01`（唯一一步 `success=false`）今天应当是红的，要标 `xfail`，
服务端上线 `execution_status` 后摘掉。

但这条 fixture **带着完整的 `steps[]`**，而 `steps[]` 今天就在线上
（`ai_sql_a2a/server.py` 的 `_artifact` 里 `"steps": [s.model_dump() ...]`）。
按上面第 1 条的过渡判据，调用方现在就能把它判成 `failed` → 不可作出处。
也就是说**这条用例今天可以是绿的**，`xfail` 会 XPASS。

**我方做的决定。** 拆成两条，两条都不许放宽：

1. `test_trust_verdict_matches_the_manifest[dp-trust-01]` —— **必过，不是 xfail**。
   断言业务结论：不可作出处。这是客户看得见的那个安全属性，今天就该成立。
2. `test_failed_step_verdict_comes_from_the_server_not_from_our_own_reduce`
   —— **`xfail(strict=True)`**。断言 `status_source == "contract"`，
   也就是这个结论**来自服务端下发的字段**而不是调用方自己 reduce。

摘掉 xfail 的时机不变（服务端上线 `execution_status`），但它盯的东西更准：
缺口的实质不是"结论错"，是"结论由谁定义"。§4.6.2 自己写着
"三个汇总数**调用方不应自己 reduce**（reduce 的口径会漂）"——
只要 `status_source` 还是 `derived`，那句警告就还成立。

**建议契约怎么改。** 把 §C 那段 `xfail` 的措辞从"这条用例应当是红的"
改成"这条用例的**判定来源**应当是红的"，并给出可断言的信号
（本方用的是 `status_source`，契约可以定一个更中立的名字）。
否则两侧会各自理解成不同的东西，而且**先做对的那一侧会被自己的用例判成失败**。

## 3. `dp-bad-06` 期望的处置在正文里找不到依据（§4.5）

**问题。** `index.json` 给 `dp-bad-06`（`database` 写成 `"ERP"`，不符合
`^[a-z][a-z0-9_]*_db$`）的期望是 `trust: not_usable`。但 §4.5 正文只说了
调用方"遇到清单外的标识符不得崩溃，退化为显示原始标识符"——那说的是
**清单外但形状合法**的情形（`hr_db`），是常规路径。

**形状不合法**该怎么处置，正文一个字都没有。而这两件事的处置正好相反：
一个照常采信，一个不可作出处。光读 §4.5 会把 `"ERP"` 当成前者。

**我方做的决定。** 形状不合法 ⇒ 整份载荷按不可信处置
（`backend/app/core/evidence.py` 的 `_malformed_database_ids`）。
理由是：这不是"不认识这个库"，是**这份载荷不是契约形状**——
一个字段跑出形状之外，别的字段也就没有理由当真。

**建议契约怎么改。** 在 §4.5 里补一句，把两种情形并排写出来：

> - 形状合法、清单外 → **常规路径**，照常采信，中文映射退化为原始标识符；
> - 形状不合法 → **载荷按不可信处置**，不要只退化展示。

## 4. `/query` 这条 transport 不在契约里，但它是今天的默认路径

**问题。** CONSUMER-TESTS 的硬规则是"两条 transport 用同一组用例"，
表里列的是 `message/send` 与 `message/stream`。但调用方今天的默认
transport 是**直连 `/query`**（`SQL_AGENT_TRANSPORT` 默认 `query`，
契约状态行自己也点了这一条），而 `/query` 的响应里逐步骤日志叫
**`step_logs`** 不叫 `steps`（`ai_sql_api/app.py` 的 `QueryResponse`）。

同一份数据、同一个 `StepLogResponse`，只是名字不同——但调用方要是没做名字
对齐，`steps` 就取不到，于是按"缺失 = 不可信"处置，**每一次直连查询都不再是
出处，而链路看起来完全正常**。§6.2 的回滚正好会把流量切到这条路上。

**我方做的决定。** 在客户端归一时把 `step_logs` 映射成 `steps`，
之后三条路径（send / stream / query）走同一个判定函数；
用例 `test_step_logs_are_normalized_to_steps` 锁住这个映射，
`test_every_data_part_is_judged_the_same_on_every_transport` 锁住三条一致。

**建议契约怎么改。** 二选一，但要选一个：

- 要么在 §4.4 承认第三条形状，把 `step_logs` ↔ `steps` 的对应写进契约面；
- 要么明写 `/query` 不受本契约约束——**但那样 §6.2 的回滚承诺就落空了**，
  因为回滚的落点不在契约的保护范围内。

## 5. `§4.6.5` 禁止回退到全局币种常量，但删掉它会退回那次事故

**问题。** §4.6.5 写着：

> `currency` / `column_units` 缺失或 `null` → 调用方**不得**擅自补币种符号或单位，
> 只能原样呈现数字并说明单位未知。**不得**回退到自己的全局常量。

在 `currency` 还没实现的今天，照这条执行等于把 `SQL_AGENT_CURRENCY` 删掉。
而那个常量当初就是为了堵一次已经发生过的业务事故：下游只返回数字，
中文回答**默认写成「元」**，接美国厂的库时报给 builder 的金额带了错误的币种。
删掉它，"不得擅自补币种"并不会让语言的默认值消失——它只是让那个默认值
重新变成隐式的。

**我方做的决定。** 保留常量，但**把来源写进句子**
（`backend/app/api/main.py` 的 `_currency_note`），三种情况说三种话：

1. 数据自己声明了 `currency`（§4.6.5 落地后）→ 按数据说，可以当事实；
2. 数据没声明、部署配了 → 按配置说，并明写「这是部署配置，**不是**本次查询
   返回的字段，不得把币种说成系统核实过的结果」；
3. 两者都没有 → 明确要求"只写数字、不要补任何币种符号，**不要默认写成「元」**"。

第 3 种情况**不是沉默**。沉默正是事故的形态。

**建议契约怎么改。** 把最后一句从"不得回退到自己的全局常量"改成两句：

> - 回退值**不得表述为数据的属性**，必须在回答里点明它来自部署配置；
> - 两者都没有时，调用方必须**主动禁止**自然语言的默认单位
>   （中文默认「元」、英文默认 `$`），只写数字并说明币种未知。

现在这条写成了一个纯禁令，而禁令挡不住语言的默认值。

## 6. 两处文档一致性

- **`CONSUMER-TESTS.md` 开头仍写「配套：`a2a-streaming-contract.md`（v1.5）」**，
  而 `fixtures/index.json` 的 `contract_version` 是 `v1.6`，
  且 tag `v1.6` 指向的就是这个内容。两侧 CI 钉在 tag 上读到的是同一份，
  所以这只是读者会困惑，不影响用例——但 v1.2–v1.5 翻的三次车都是从
  "文档说的和实际是两回事"开始的。
- **`§1③` 的第三档没有任何自动检查。** CONSUMER-TESTS 的「没有覆盖什么」
  已经诚实写了这一点。我方按建议加了启动断言
  （`backend/app/core/preflight.py::check_timeout_budgets`：外层工具超时必须
  **严格大于** send 预算，不满足拒绝启动；另外在 `SQL_AGENT_TRANSPORT` 还是
  `query` 时把 send 放宽到 45s 以上会告警）。
  **服务端那侧没有对应的检查**，建议契约把这条断言写成两侧都要做的事，
  或者至少写明"这一条只有调用方能检查"。
