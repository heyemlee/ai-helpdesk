# 内部只读试点：上线前检查单与边界（2026-09-08）

> 这份文档不是系统介绍，是**上线前的 go / no-go 清单**。
> 每一条都标了它是怎么来的：`【实测】` = 在当前运行的这套栈上跑过；
> `【测试】` = 有自动化用例锁住；`【待填】` = 业务事实，只有你能填。
>
> 范围决定：第一次上线是「已认证 + 同权限内部人员 + 只读 + 有限库表 + 低并发 +
> 人工可核实」的试点。审查报告的原话是：试点结果**不能外推**成多客户生产能力。

## 0. ⛔ 上线前必须先做的一件事：**重建镜像并重启**

**【实测 2026-09-08】当前正在运行的这套栈，跑的是 8 月 31 日的代码——
三轮修复没有任何一条在里面。**

证据（都在运行中的容器里直接查的）：

| 检查 | 结果 |
| --- | --- |
| `docker inspect ai-helpdesk-app` 的镜像创建时间 | **2026-08-31**（9 天前） |
| 容器内 `find / -name preflight.py` | **没有这个文件** |
| 容器内 `find / -name evidence.py -path "*core*"` | **没有这个文件** |
| 容器内 `grep -c run_startup_checks api/main.py` | **0** |

也就是说这些**全都不在运行的系统里**：启动断言（P0-2）、信任判定
`evidence.py`（P0-3）、部署范围断言、超时档位联动、`step_logs`/`steps` 双名兼容。

**行为上的实证**，不只是文件对比：

```
POST /auth/token  （不带任何 API key）
→ HTTP 409  {"detail":"未配置 AI_HELPDESK_AUTH_SECRET，令牌鉴权未开启"}
```

**409 而不是 401**：请求**穿过了**鉴权依赖，只是因为没配 secret 才停下——
这正是 P0-2 那个 fail-open（`if not _API_KEY: return`）。修复后的代码里
`require_admin_key` 永不放行，而且 `APP_ENV=production` 配不全时**进程根本起不来**。

而当前容器的环境是：

| 变量 | 当前值 |
| --- | --- |
| `APP_ENV` | **production** |
| `AI_HELPDESK_API_KEY` | **空** |
| `AI_HELPDESK_AUTH_SECRET` | **空** |
| `AI_HELPDESK_TOKEN_ISSUER_CIDRS` | **空** |
| `AI_HELPDESK_DEPLOYMENT_SCOPE` | **未设置** |
| `AI_HELPDESK_PROTECT_CHAT` | false |

**这套组合在新代码下会直接拒绝启动。它现在能跑，唯一的原因就是新代码不在里面。**

> **所以第 0 条是：`docker compose build` + 重启，然后确认它真的起不来。**
> 起不来是对的——那说明断言生效了。按它报的名字逐项配齐，直到它正常启动。
> **如果重建后它照样起来了，说明镜像没换成功，回到这一条。**

## 1. 上线前检查单

### 1.1 必须做（缺一条就不要上）

- [ ] **重建两个镜像并重启**（见第 0 节）。镜像 `ai-helpdesk-backend:local` /
      `ai-helpdesk-frontend:local` 已在本机构建成功【实测】，但**当前容器用的不是它们**。
- [ ] **配齐生产必需的四项**，直到进程能正常启动：
      `AI_HELPDESK_API_KEY` / `AI_HELPDESK_AUTH_SECRET` /
      `AI_HELPDESK_PROTECT_CHAT=true` / `AI_HELPDESK_TOKEN_ISSUER_CIDRS`（网关网段）。
- [ ] **声明部署范围**：`AI_HELPDESK_DEPLOYMENT_SCOPE=internal_single_tenant`。
      故意没有默认值——漏配和想清楚了配成这个，风险不同。
- [ ] **收起对外端口**。【实测】当前 Postgres（5433）、Redis（6379）、
      Grafana（3000）都绑在 `0.0.0.0`。试点只需要暴露入口，
      数据库和监控不该从主机外可达。
- [ ] **决定 SQL 委派开不开**。【实测】当前 `SQL_AGENT_URL` 未设置、
      `ai-sql-agent` 容器没有在跑——**业务数据查询这条路整个是关的**。
      要在试点里用它，得先把它部起来并按第 2 节确认边界。
- [ ] **【待填】确认可查的库表白名单**，并在 ai-sql-agent 的 key 策略里配好。
- [ ] **【待填】确认试点用户名单**，并确认他们权限相同（这是本次范围的前提）。

### 1.3 明确没有的（上线时要知道自己缺什么）

| 缺什么 | 影响 | 为什么试点期可接受 |
| --- | --- | --- |
| **GitHub CI 一次都没跑过** | 门禁不是 required check，带红的东西也能合 | 【实测】`gh workflow run` 返回 `HTTP 422: Actions has been disabled for this user` —— 账号级禁用，三个仓库全中，**只能走 GitHub Support**。本机门禁有记录可替代 |
| **真实模型评测基线已跑出，门禁 FAIL** | 跨库准确率与静默错误率不达标——回答本身可能是错的，且不带任何提示 | 【实测 2026-09-08】3 轮取均值，绑定 model=`claude-sonnet-5`、commit=`ee920e9`、dataset 见 sha256。单库执行准确率 89.6%✅（线 85%）；**跨库执行准确率 73.3%❌（线 90%，区间 [72%, 76%]）**；**静默错误率 10.0%❌（线 3%，区间 [8.67%, 11.33%]）**——即每 10 次问答里约 1 次是"跑通了、有结果、没有任何提示、但答案是错的"；平均进图字段占比 43.6%❌ 压线超（线 40%）。字段召回率（评测集/留出集）、误报率、检索落差四项达标。**这份基线跑在内置演示语义层，不是当前部署的 `sim_erp/semantic`——两边库结构未必一致，数字不能直接当成当前部署的准确率**，只能说明同一套 pipeline 代码在标准夹具上的水平。完整数据、题目级明细、复现方法见 `ai-sql-agent/benchmark/baseline/2026-09-08/README.md`。**⚠️ 更正（复核 450 条题次的逐题明细之后）：「禁用跨库」这个建议不够。** 按类别拆开看，最差的不是跨库，是**多表连接**——而它根本不在门禁的失败项里：`multi_join` **29.3%** ／ `cross_db` **18.7%** ／ `aggregation` 8.0% ／ `time_range` 4.0% ／ `single_table` **0%** ／ `having` **0%**。只禁 `cross_db` 之后静默错误率仍有 **8.3%**（线的 2.8 倍）；同时禁 `cross_db` 与 `multi_join` 才降到 **3.0%**——**恰好压线，没有余量**。真正干净的只有 `single_table` 和 `having` 两类。<br>另一个要点：`false_alarm_rate` 只有 5.9%（线 20%），说明风险提示机制本身很保守、不乱报——问题是**该报的时候没报**。所以这不是「把阈值调低、多报几条」能解决的，要让多连接／跨库场景主动降低置信并把不确定说出来。 |
| **最小授权没在真实业务库执行过** | 应用层是唯一一道防线 | 同权限范围里没有跨用户越权面。工具和 runbook 已就绪（`ai-sql-agent/deploy/least-privilege-runbook.md`） |
| **`/auth/token` 不是登录系统** | 网关被攻破 = 可冒充任意用户 | 同权限内部人员，冒充谁都一样；且已绑定网段。对接方案见 `docs/auth-token-integration.md` |

## 2. 这次试点是什么 / 不是什么

| 维度 | 范围 |
| --- | --- |
| 用户 | 已认证的内部人员，**且所有人权限相同**　【待填：哪些岗位、多少人】 |
| 数据 | **只读**，系统不写任何业务库 |
| 库表 | 有限白名单　【待填】 |
| 并发 | 低　【待填：预期峰值】 |
| 核实 | 每个回答带 `trace_id`，可追到实际 SQL 和记录 |
| 时长 | 【待填：周期 + 中期回顾时间点】 |

**这次试点不是：**

- ❌ **不是多租户。** 所有用户看到的数据范围完全相同。行范围（RLS）和
  impersonation 取交集虽然实现了，但**试点期不启用**，也没在任何真实业务库配置过。
- ❌ **不是面向客户的产品。** 任何"让客户查自己订单"的用法都在范围之外。
- ❌ **不是经过生产验证的系统。** 没有可绑定版本的真实流量、SLO、事故与恢复记录。

## 3. 谁在守边界

| 边界 | 守在哪 | 强度 |
| --- | --- | --- |
| 只有认证过的人能用 | `preflight.check_security_config`，生产模式缺配即启动失败 | 代码强制（**需第 0 条生效后**） |
| 令牌只能从网关签发 | `AI_HELPDESK_TOKEN_ISSUER_CIDRS`，校验直连对端，不看 `X-Forwarded-For` | 代码强制（同上） |
| 「这是单租户部署」 | `AI_HELPDESK_DEPLOYMENT_SCOPE`，未声明即拒绝启动；声明单租户却开 impersonation 也拒绝 | 代码强制（同上） |
| SQL 不能越权 | 执行器入口统一鉴权 + sqlglot AST，解析不出来一律拒绝 | 代码强制 |
| 未知角色不给权限 | `_resolve_policy` → `deny_all()` | 代码强制 |
| 带风险/降级/失败的结果不作出处 | `evidence.assess()`，缺字段即不可信 | 代码强制（同上） |
| 数据库只读 | 只读事务 + 只读账号 + 应用层三层 | 代码强制 |

> **括号里的「需第 0 条生效后」不是形式**：这些断言全都在新代码里，
> 而新代码不在当前运行的容器里。重建之前，这一整列的强度都是**零**。

## 4. 出问题怎么办

- **数字看着不对** → 拿 `trace_id` 查审计，能看到实际执行的 SQL 和命中的记录。
  **试点期请把每一次不对都记下来**——这份记录比评测集更贴近真实分布。
- **系统说"没查到"** → 分两种：`no_data`（查到了，答案是没有）和 `failed`（没查成）。
  前者是事实，后者是故障，回答措辞不同。
- **转人工没反应** → 工单走 outbox，失败会记 `ticket_notify_failures_total` 并升级。查那个指标。
- **要恢复数据** → `bash backend/docker-deploy.sh restore <备份目录>`。
  RTO 实测 17 秒。**注意 2026-09-08 之前的旧备份恢复不了 Redis**（脚本会明确警告）。
- **联系谁** 【待填】

## 5. 停止条件（要有人签字知道）

1. 出现一次**危险错误**：给出具体金额/日期/订单状态，**没有任何不确定提示**，而事实是错的。
2. 出现任何**越权读取**：查到了白名单之外的库表。
3. 有人开始把它当**多租户**用：出现按用户区分数据范围的需求或配置。
4. 【待填：业务方自己的红线】
