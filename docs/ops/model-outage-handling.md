# 模型服务不可用时的处理：现状、已知限制与未完成的验证

> **状态（故障处理收尾时）：开发与离线验证完成；新后端尚未重启生效；
> 真实中继与两项目成功联调待完成。**
>
> 标注沿用本目录的写法：`【离线】` = 有自动化用例锁住，模型那头接的是假中继，
> 没有模型参与；`【界面】` = 用只回放录制夹具的假后端在浏览器里看过；
> `【未验证】` = 还没有在真实环境里看过。这份文档里**没有一条**是 `【实测】`。

---

## 1. 起因

从某天晚上 20:39 起，中继对配置的 Key 返回
`401 {"error": "Invalid API key", "message": "API key is disabled"}`。当时的表现：

- 一条提问打出 6～8 次请求（意图、改写、重排、自纠错再来一轮、专家、通用 Agent 兜底），
  全部 401，每个调用点都在自己的 `except` 里"成功降级"；
- 没答上来的问题被当成"需要人工"，每条各开一张业务工单；
- 会话摘要失败后，客户的原话被一句"摘要生成失败"的占位顶掉；
- 评测照常把几十条用例跑完，交出一份全是失败默认分的报告。

## 2. 现在的行为

| 场景 | 行为 | 依据 |
| --- | --- | --- |
| 凭证被明确拒绝（401；错误体明说不被允许的 403；402 或错误体明说额度用尽） | 同一份配置（供应商 + 地址 + 凭证）的模型调用不再出网，直到重启或解除 | 【离线】`tests/test_llm_guard.py` |
| 普通 429、说不清原因的 403 | 有限退避（5s～60s / 30s～600s，服务端给了 `retry-after` 就听它的，封顶 900s），到期自动放行 | 【离线】同上 |
| 停机期间的提问 | 第一条出 1 次请求，之后 0 次；返回 `service_unavailable=true`、`handoff=false`，**不建工单** | 【离线】`tests/test_model_outage.py` |
| 客户明确要求人工、CRITICAL 紧急度 | 走规则，不经模型，照常转人工并建单 | 【离线】同上（CRITICAL 在停机期间没有单独用例，和明确要求人工是同一个分支） |
| 置信度阈值、策略拦截等原有升级条件 | 没有改动，照常转人工并建单 | 【离线】`tests/test_agent_orchestrator.py` 的既有用例 |
| 检索里的改写或重排调用失败 | 如实报"没判"（`evidence_ok=null`），不再补检一轮 | 【离线】`tests/test_model_outage.py` |
| 专家因凭证被拒 | 不再用同一把凭证调通用 Agent | 【离线】同上 |
| 会话摘要失败 | 历史原样保留，不写占位；120 秒冷却后才重试 | 【离线】同上 |
| 没答上来的轮次 | 不提炼用户画像；降级出来的意图不进缓存 | 【离线】同上 |
| 评测遇到保护状态 | 立即中止，已完成的结果另存 `baseline.incomplete.json`，不写基线、不能提升 | 【离线】同上 |
| 工作台 | "系统提示 · 未作答"和原因，不出工单卡；管理页分开报"服务在线"和"模型不可用" | 【界面】夹具在 `frontend/src/test/fixtures/outage/` |

"不建工单"**只限模型或基础设施故障**。它不是一个"停机时不转人工"的开关。

## 3. 怎么恢复

1. 处理凭证或额度（这一步在本系统之外）。
2. 重启后端，**或者**调一次受保护的 `POST /skills/reload`——它同时解除保护。
3. 下一条真实请求会重新出网去试；还不行的话，那一次调用会重新触发保护。

没有定时探测。`GET /health` 的 `llm.available` / `llm.unavailable_reason` 读的是进程里
记下的状态，查它不会调模型；工作台的「管理与诊断 → 概览」显示的就是这两项。

## 4. 已知限制

- **状态只在单个进程里。** 员工实例和客户实例各记各的，各自要被拒一次才知道；多 worker 同理。
- **已在途的并发请求仍会各发一次。** 第一个拒绝回来之前已经发出去的请求收不回来
  （并行的两个专家、同一时刻的几个用户）。
- **一次 401 就一直挡。** 中继偶发的误报也要人工恢复；额度按周期自动恢复的也一样。
  这是有意的取舍：等再久它也不会自己好的那几类，不该靠重试去试。
- **错误体的归类靠措辞。** 中继的错误体常常没有标准类型字段，403 和额度用尽是按
  常见说法认的；认不出的 403 落到有限退避，不会被判成永久。
- **摘要持续失败时工作记忆只增不减。** 由 24 小时过期兜底；恢复后第一次压缩会一次
  处理全部积压，那一次的提示词也会带着全部积压。
- **不在保护范围内的出网调用：** 独立凭证的远端 Embedding 和重排（它们各自有
  "失败一次、本进程改用本地"的降级）。
- **审计日志只记"这是一条系统提示"，不记原因。** 刷新后的历史能标出"未作答"，标不出为什么。
- **压测脚本会把"不可用"的 200 响应计为成功**，那时的延迟数字没有意义（后端此时不出网）。
- **`POST /skills/reload` 的保护取决于 `AI_HELPDESK_API_KEY`。** 没配这把钥匙的实例上，
  任何人都能解除保护——和这个接口原有的状况一致。

## 5. 尚未完成的验证

- **新后端还没有重启过。** 生产和练习环境跑的仍是旧进程，上面这些行为要重启后才生效；
  镜像没有重建。
- **【未验证】真实中继下的表现。** 实际见过的只有那一条 401 错误体。真实的 403、429、

## 6. 离线验证怎么复跑

全部不需要模型、Redis 或 Postgres。后端要在**不含 `.env` 的副本**里跑——在工作区里直接
跑，`load_dotenv` 会读到真实配置：

```bash
# 后端（副本里没有 .env；占位 key 只为满足启动期校验）
env -u ANTHROPIC_BASE_URL ANTHROPIC_API_KEY=test-key python -m pytest -q
env -u ANTHROPIC_BASE_URL ANTHROPIC_API_KEY=test-key \
  python -m pytest -q tests/test_llm_guard.py tests/test_model_outage.py

# 前端
npm run typecheck && npm test && npm run build
```

当时的结果：后端 788 通过、20 跳过（带契约夹具 866 通过、4 跳过）；前端 185 通过，
生产构建通过。另外在临时副本里把 14 处修复逐个撤掉，每一处都有用例变红。

前端回放用的夹具由后端的真处理函数生成，后端改了这个场景下发出去的内容时
`test_frontend_outage_fixtures_are_what_the_backend_sends` 会红。重新生成：

```bash
AI_HELPDESK_RECORD_FIXTURES=<仓库>/frontend/src/test/fixtures/outage \
  python -m pytest tests/test_model_outage.py -k fixtures
```
