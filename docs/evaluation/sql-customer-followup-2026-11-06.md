2. 规划按所问事实决定最少必要步骤，补充“多个候选库仍只需一步”的独立示例；区分整体订单状态与生产工序，避免将售后单和补件明细拼成不同粒度的行。布尔计算输出约定的 1/0，未知保留 NULL；日期和业务状态原值保留。
3. 先重点回归 c02/c10/c18/c24，再用固定版本跑完全部 24 题。初次重点回归是 2/4，暴露了 c02 工序被误当整体状态、c24 中文布尔格式的问题；修正后同样四题全部通过。保留两轮结果，不从最终报告中删除失败尝试。
4. 增加三道独立的真实模型规划检查：只问整体状态只查订单库；明确同时问订单状态和工序仍查两个库；承运商筛选后求合同总额仍按跨库关联键拆步。三题全通过，仅证明规划结构，不计入 24 题或端到端查询成功率。

## 剩余问题

### c03：我这单 J26-00044 还要多久能送到？

程序错因：`extra_columns`。

```json
{
  "gold": [
    {
      "delivery_date": "2026-07-02"
    }
  ],
  "last_step": [
    {
      "order_no": "J26-00044",
      "delivery_date": "2026-07-02",
      "remaining_days": -127.0
    }
  ],
  "flag_reasons": []
}
```

正确计划交付日期已返回，模型另外计算了距计划日期的天数，导致结果超过“所问标准列 + 一个标识”的现行限制。该题的自然问法“还要多久”和仅要求日期的标准答案存在表达范围差异。此次不在看到新输出后改题或放宽规则，保留失败；负的天数代表计划日期已过，不能当成实际到货预测。后续应先独立明确相对时间题的参考日期、必要事实及允许的补充字段，再冻结新版题集。

### c11：J25-00137 我们报的几个问题现在都处理好了吗？

程序错因：`wrong_values`。

```json
{
  "gold": [
    {
      "issue_type": "安装问题",
      "service_status": "已解决"
    },
    {
      "issue_type": "质量问题",
      "service_status": "处理中"
    }
  ],
  "last_step": [
    {
      "description": "Filler does not fit field condition",
      "service_status": "已解决"
    },
    {
      "description": "Finish defect on door front",
      "service_status": "处理中"
    }
  ],
  "flag_reasons": []
}
```

两条售后记录的处理状态均与记录一致，但模型用问题描述 description 区分问题，gold 要求问题类型 issue_type，因此原值匹配失败。该结果不证明售后状态答错；问题标识字段的等价条件尚未纳入当前判分。后续应先明确可接受的记录标识和关联校验，再冻结标准；不能只要出现相同状态就算同一问题回答正确。

### c23：Why hasn't J25-00094 shipped yet?

程序错因：`wrong_values`。

```json
{
  "gold": [
    {
      "delivery_notes": "access blocked by other trades；配送失败，待重新配送"
    }
  ],
  "last_step": [
    {
      "order_no": "J25-00094",
      "production_notes": null
    }
  ],
  "flag_reasons": []
}
```

这道是实际漏查，不是等价表达问题。规划把未发货原因直接对应到生产备注，查询只得到 NULL 就结束；配送表实际记有 access blocked by other trades（现场被其他工种阻挡），但没有被查询。检索召回记录为命中，问题发生在后续规划选择证据来源。上轮已查到配送原因但因多列而未通过，本轮虽然缩窄输出，仍未解决这道题，且遗漏了关键事实。后续应优先校正“原因来源尚不确定”时的查询覆盖，区分无关扩查和查明原因所必需的补查，并用独立的生产阻塞、配送阻塞及无原因记录案例验证；不能把所有原因题硬编码到配送库。
